# TikTok LIVE 自動取得の受信検証

LIVE BOOSTのような配信データ活用をKazzCompanyに取り入れるための、1枠用の受信プログラムです。**本番導入前の検証用**です。Node.js 22以上で動作し、追加パッケージは不要です。

## 現在できること

- Euler StreamのWebSocket APIから、公開配信の通知を受信する接続コード。
- 通知の種類・通知件数・観測できたユーザーID数・フィールド名を保存。
- 正確なメッセージIDとルームIDがある通知の重複除外。
- 関連メッセージの種類を記録し、グローブ等の獲得・使用が識別できるか調べる準備。
- 切断理由と再接続の記録。通信エラーを「配信終了」と扱わない。

**実配信接続は未検証**です。APIキーと、同意を得た検証対象のTikTok @IDが必要です。LIVE BOOSTのアカウントや契約は使いません。

既存アイテムの加算・減算、データベースへの書き込み、通知送信は実装していません。ギフトの通知をそのままグローブ数へ変換することもありません。

## 外部接続せず試す

リポジトリのルートで実行します。

```bash
node --test tools/live-probe/core.test.mjs
node tools/live-probe/probe.mjs --replay tools/live-probe/fixture.jsonl
```

`fixture.jsonl`はすべて架空のテストデータです。通知形式を確認するためのデータで、グローブ取得の実例ではありません。再生結果はギフト**通知**2件、重複除外1件、観測ユーザー1人、検証済み在庫操作0件です。

## 実配信で試すための準備

1. [Euler Stream](https://www.eulerstream.com/)でアカウントとAPIキーを用意する。無料枠の対象・残量をアカウント画面で確認する。
2. APIキーを**チャット、GitHub、HTMLへ貼らず**、実行するPC・サーバーの秘密設定へ入れる。
3. 検証対象の公開配信が始まってから、受信プログラムを起動する。

安全な場所に置いた設定ファイルの形式：

```dotenv
EULER_API_KEY=取得したキー
```

```bash
node --env-file=/安全な場所/live-probe.env tools/live-probe/probe.mjs --creator @検証対象のID --minutes 15
```

上記の`@検証対象のID`は実際の英数字IDへ置き換えます。既定15分、最長30分で停止します。途中停止はCtrl+C。再接続は最大3回で、認証・権限・上限エラーの場合は停止します。プログラムはアカウント登録、プラン変更、有料追加機能の有効化を行いません。API利用自体が契約枠を消費するため、実行前に枠を確認してください。

**スマホを閉じても継続する本番自動取得には、常時動く受信環境か提供元の通知機能が必要です。** この段階のプログラムは実行中だけ記録する検証用です。

## 出力と検証用データ

`tools/live-probe/captures/ランダムなID/summary.json`に結果を保存します。このディレクトリはGit管理の対象外です。

通常はコメント本文や名前を保存せず、件数とフィールド名だけを記録します。獲得・使用の内容を調べる場合だけ、`--capture-payloads`を追加してください。名前やコメントを含む可能性のある受信データを`events.jsonl`に保存します。データは端末内で確認し、**公開リポジトリ・公開ページには掲載しません**。APIキー等の既知の認証情報は除去しますが、個人情報の匿名化を保証する機能ではありません。検証後に不要な記録を削除してください。

データ保存は20MiBまで、処理は100,000通知までです。上限や形式不一致が起きた場合は結果に表示します。未対応形式を「受信できた」とは数えません。

| 確認項目 | 判断すること |
| --- | --- |
| 通常コメント・ギフト | 実際の画面と受信記録が対応するか |
| 連続ギフト | 途中通知と確定通知を区別できるか。通知数をギフト数にしない |
| 🥊の獲得・使用 | 所持者の正確なID、種類、増減、時刻が取得できるか |
| 切断・再接続 | 重複、欠落、配信終了との誤認がないか |
| 既存残数・有効期限 | 初期値や正確な期限が取れるか。取れない場合は初期登録・訂正が必要 |

`itemCandidateEventTypes`は候補の一覧です。バトル等の通知を含み、グローブの獲得・使用が取得できた証拠ではありません。`verifiedInventoryOperations`は常に0です。

`observedUserCount`は受信通知に正確な数値IDが含まれた人だけを数えます。全視聴者数、同接、初見数、滞在時間とは異なります。名前だけで同一人物とは判定しません。開始前や切断中の履歴は復元しません。

## 次に組み込む順序

1. 1枠で実配信の受信精度を確認する。
2. 受信側でユーザーIDと通知IDを保持し、連続ギフト・重複・切断を処理して貢献記録を作る。
3. 配信開始・終了の確認を配信者ホームへ結びつける。接続失敗は「状態不明」にする。
4. グローブ等は種類・所持者・獲得・使用・期限を実データで確認できたものから追加する。初期残数と手動訂正を扱い、自動記録との二重加算を防ぐ。

対象リポジトリの`index.html`は端末内保存の無料版です。共有版への具体的な反映先は、対象の管理ページとサーバー構成を確認してから接続します。

調査根拠と提供元の条件は [導入調査](../../docs/tiktok-live-auto-capture.md) にまとめています。
